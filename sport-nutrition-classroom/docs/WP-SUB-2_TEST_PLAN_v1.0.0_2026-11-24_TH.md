## 1. วัตถุประสงค์

แผนนี้กำหนดการตรวจสอบในสภาพแวดล้อม TEST สำหรับการอัปโหลดไฟล์จริงไปยัง Google Drive และการควบคุมการเข้าถึงไฟล์ของระบบ Submission Management ครอบคลุมการตรวจสอบชนิดและเนื้อหาไฟล์ การสร้างไฟล์ในโฟลเดอร์ TEST ที่กำหนด การบันทึกข้อมูลไฟล์ในสถานะรอแนบ การแนบไฟล์เข้ากับ Submission การตรวจสอบสิทธิ์ของผู้ใช้และสิทธิ์ใน Google Drive ตลอดจนการตรวจสอบการกู้คืนเมื่อเกิดข้อผิดพลาดบางกรณี

เอกสารนี้เป็นแผนการทดสอบเท่านั้น ไม่ใช่การอนุญาตให้พัฒนาโค้ด เรียกใช้ Google Apps Script (GAS) สร้างโฟลเดอร์ อัปโหลดไฟล์ เปลี่ยนสิทธิ์ ลบหรือย้ายไฟล์ ติดตั้งใช้งานระบบ หรือเปลี่ยนแปลง Production

### 2.1 พฤติกรรมของ Source Code ที่ตรวจพบ

- `FileManagement.gs` รองรับ PDF, Word/PowerPoint/Excel รูปแบบเดิม, Office Open XML (OOXML) ของ Word/PowerPoint/Excel, ข้อความธรรมดา, JPEG และ PNG
- ระบบจำกัดขนาดไฟล์ไว้ที่ 4 MiB (`4 * 1024 * 1024` ไบต์) โดยตรวจความยาว Base64 จำนวนไบต์หลังถอดรหัส MIME type ที่แจ้ง นามสกุลไฟล์ในกรณีที่เกี่ยวข้อง และลายเซ็นของไฟล์ สำหรับ OOXML ระบบแตกไฟล์เพื่อตรวจเส้นทางไฟล์ภายในที่จำเป็น และจำกัดขนาดข้อมูลหลังแตกไฟล์ไว้ที่ 20 MiB
- การอัปโหลดต้องใช้ Script Property ชื่อ `SNC_SUBMISSION_FOLDER_ID` ตัวจัดการคำสั่งตรวจว่าสิทธิ์การแชร์ของโฟลเดอร์เป็น `PRIVATE` จากนั้นสร้างไฟล์ใน Drive และพยายามเพิ่มสิทธิ์ Viewer ให้ผู้ส่งไฟล์
- เมื่ออัปโหลดสำเร็จ ระบบเพิ่มแถวใน `SubmissionFiles` โดยกำหนด `SubmissionID` เป็นเครื่องหมายสถานะรอแนบรูปแบบ `STAGED:<userId>:<assignmentId>` แล้วบันทึกเหตุการณ์ `SUBMISSION_FILE_UPLOADED` ใน `AuditLogs`
- หากเพิ่มข้อมูลไฟล์ไม่สำเร็จ ระบบพยายามย้ายไฟล์ Drive ที่สร้างขึ้นไปยังถังขยะ หากบันทึก Audit ไม่สำเร็จ ระบบพยายามลบแถวข้อมูลไฟล์และย้ายไฟล์ไปยังถังขยะ
- คำสั่ง `file.access` ปฏิเสธกรณีไม่พบข้อมูลหรือไฟล์ยังอยู่ในสถานะรอแนบ จากนั้นตรวจสิทธิ์ระดับแอปพลิเคชันของ Submission ก่อนส่งคืน URL และข้อมูลไฟล์
- ระหว่างสร้างหรือแก้ไข Submission, `SubmissionManagement.gs` ตรวจว่าไฟล์ที่รอแนบถูกอัปโหลดโดยผู้ส่งหรือสมาชิกกลุ่มที่ยังมีสถานะใช้งานอยู่ใน Assignment เดียวกัน ระบบพยายามให้สิทธิ์ Viewer แก่ผู้ส่ง สมาชิกกลุ่มที่ยังใช้งาน และผู้สอนที่ได้รับมอบหมายในรายวิชา
- กระบวนการย้อนกลับ (Rollback) ของ Submission พยายามคืนค่าข้อมูลไฟล์ ลบแถว URL ที่สร้างขึ้น ลบ Submission ที่สร้างใหม่ คืนค่าสถานะล็อกกลุ่ม และเพิกถอนสิทธิ์ Viewer ที่เพิ่มขึ้น การย้อนกลับนี้เป็นการชดเชยการเปลี่ยนแปลงหลายส่วน ไม่ใช่ธุรกรรมที่ย้อนกลับได้พร้อมกันโดยอัตโนมัติ
- `NotificationManagement.gs` มีพฤติกรรมส่งการแจ้งเตือนผ่าน LINE และ `UrlFetchApp` การทดสอบ WP-SUB-2 ต้องป้องกันทุกเส้นทางการแจ้งเตือนไม่ให้เชื่อมต่อ LINE หรือเครือข่ายภายนอกจริง

### 2.2 ข้อจำกัดสำคัญของการตรวจสอบ

การตรวจ Source Code แบบอ่านอย่างเดียวไม่ใช่หลักฐานว่าระบบทำงานจริงแล้ว โดยเฉพาะประเด็นต่อไปนี้

- การตรวจว่าโฟลเดอร์เป็น `PRIVATE` เพียงอย่างเดียว ไม่ได้พิสูจน์ว่าสิทธิ์ที่มีผลจริง (Effective ACL) ของไฟล์ทุกไฟล์ปลอดภัย หรือ URL ของไฟล์จะไม่สามารถเปิดได้โดยผู้ไม่มีสิทธิ์
- ขั้นตอนอัปโหลดพยายามเพิ่มสิทธิ์ Viewer ให้ผู้ส่งเฉพาะเมื่อพบข้อมูลผู้ใช้และอีเมลที่ตรงกัน แต่ Source Code ปัจจุบันไม่ได้ปฏิเสธการอัปโหลดอย่างชัดเจนเมื่อไม่พบผู้ใช้หรืออีเมล ต้องตรวจสอบพฤติกรรมนี้และถือเป็นประเด็นที่อาจต้องแก้ไข ห้ามสรุปเองว่าปลอดภัย
- กระบวนการ Rollback บางจุดดักจับข้อผิดพลาดย่อยและบันทึกข้อความทั่วไป การทดสอบจึงต้องตรวจสถานะไฟล์ใน Drive และข้อมูลใน Sheet จริงหลังจำลองข้อผิดพลาดทุกครั้ง
- เจ้าของไฟล์ การสืบทอดสิทธิ์จากโฟลเดอร์แม่ การใช้ Shared Drive และข้อจำกัดระดับบัญชี Google อาจส่งผลต่อการเข้าถึง ดังนั้นต้องยืนยันโฟลเดอร์ TEST และบัญชีที่ใช้ทดสอบก่อนเริ่มงาน

## 3. วัตถุประสงค์การทดสอบ

1. ตรวจว่าไฟล์ชนิดที่ระบบรองรับสามารถอัปโหลดไปยังโฟลเดอร์ TEST ที่กำหนด และสร้างข้อมูลไฟล์ในสถานะรอแนบได้ถูกต้อง
2. ตรวจว่าไฟล์ที่ไม่ถูกต้อง เสียหาย ขนาดเกิน หรือชนิดไฟล์ไม่ตรงกับเนื้อหา ถูกปฏิเสธก่อนสร้างไฟล์ใน Drive
3. ตรวจวงจรการทำงานของไฟล์ตั้งแต่การอัปโหลดจนถึงการแนบเข้ากับ Submission
4. ตรวจสิทธิ์ของแอปพลิเคชันและสิทธิ์ Drive ที่มีผลจริง สำหรับผู้ส่ง สมาชิกกลุ่มที่ยังใช้งาน ผู้สอนที่ได้รับมอบหมาย สมาชิกกลุ่มเดิมที่พ้นสถานะ และผู้ใช้ที่ไม่เกี่ยวข้อง
5. ตรวจการทำงานเมื่อเกิดข้อผิดพลาดและ Rollback ในกรณีที่ได้รับอนุมัติ โดยไม่เรียก Runner ที่ทำรายการถาวรซ้ำ
6. ตรวจสอบไฟล์ Drive แถว SubmissionFiles แถว Submission การเปลี่ยนสถานะล็อกกลุ่ม และ AuditLogs ที่เกิดจากการทดสอบ ด้วยรหัสระบุข้อมูลจำลองที่แน่นอนใน Manifest ซึ่งจำกัดสิทธิ์การเข้าถึง พร้อมไม่เปิดเผยรหัสดิบใน Log ทั่วไป
7. รักษาข้อมูลและหลักฐานพื้นฐานทั้งหมดของ WP-SUB-1

## 4. ขอบเขตการทดสอบ

### 4.1 รายการที่อยู่ในขอบเขต

- สภาพแวดล้อม TEST เท่านั้น
- ไฟล์ไบนารีจริงในโฟลเดอร์ Google Drive TEST ที่กำหนดและตรวจสอบสิทธิ์แล้ว
- Handler ของระบบ TEST ที่ได้รับอนุมัติ ได้แก่ `file.upload`, `file.access`, `submission.create` และ `submission.revise` เฉพาะเมื่อได้รับอนุมัติ
- บัญชีทดสอบจำลองที่มีอยู่แล้วใน Core Fixture ที่ได้รับอนุมัติ โดยต้องตรวจสอบแบบอ่านอย่างเดียวอีกครั้งก่อนทดสอบ
- เส้นทาง Assignment รายบุคคลและ Assignment แบบกลุ่ม รวมถึงกรณีไฟล์รอแนบถูกอัปโหลดโดยสมาชิกกลุ่มที่ยังใช้งาน
- การตรวจสิทธิ์ Drive ที่มีผลจริงโดยใช้บัญชีทดสอบแต่ละบทบาท
- การจำลองข้อผิดพลาดและการตรวจสอบหลังทดสอบแบบอ่านอย่างเดียว เฉพาะกรณีที่ได้รับอนุมัติชัดเจน

### 4.2 รายการที่อยู่นอกขอบเขต

- Production หรือ Branch `main`
- WP-SUB-3 ซึ่งครอบคลุม API, LIFF, Browser E2E หรือ UAT บนระบบที่ติดตั้งใช้งานแล้ว
- การส่งข้อความ LINE, `UrlFetchApp`, การเชื่อมต่อเครือข่ายภายนอก การส่งอีเมล หรือการเขียนข้อมูลใน NotificationLogs
- การสร้าง/ลบ/เรียกใช้ Trigger การย้ายข้อมูล การเปลี่ยน Schema การ Deploy การทดสอบถดถอยในวงกว้าง หรือ Cleanup
- การเปลี่ยนแปลงระบบยืนยันตัวตน การแฮชรหัสผ่าน GPS หรือโมดูลอื่นที่ไม่เกี่ยวข้อง
- การแก้ไขข้อมูลใน Sheet ด้วยตนเองเพื่อจำลองผลการทำงานของ Handler
- ข้อมูลจริงของนักศึกษา ผู้สอน หรือข้อมูลส่วนบุคคล
- การเรียก Runner ของ WP-SUB-1 หรือ Runner ที่ทำรายการถาวรก่อนหน้านี้ซ้ำ

| ช่วงเวลาทดสอบ | เจ้าของกำหนดช่วงเวลาที่ไม่มีการรัน TEST หรือการใช้งานอื่นซึ่งอาจกระทบโฟลเดอร์และ Fixture |

หากรายการใดไม่ทราบ ขัดแย้งกัน หรือตรวจสอบแบบอ่านอย่างเดียวไม่ได้ ให้หยุดก่อนพัฒนา

## 6. ชุดไฟล์ทดสอบจำลอง

ใช้ไฟล์สังเคราะห์ที่ไม่มีข้อมูลลับและสร้างขึ้นเพื่อการทดสอบเท่านั้น แต่ละไฟล์ต้องทราบจำนวนไบต์ MIME type นามสกุล และลายเซ็นของไฟล์ ห้ามใช้เอกสารจริง

| Fixture | วัตถุประสงค์ | ข้อกำหนดรูปแบบ/ขนาด |
|---|---|---|
| F01 | อัปโหลด PDF ที่ถูกต้อง | PDF ขั้นต่ำที่มีโครงสร้างถูกต้อง ขนาดมากกว่า 0 และน้อยกว่า 4 MiB |
| F02 | อัปโหลด JPEG ที่ถูกต้อง | JPEG ที่ถูกต้อง ขนาดน้อยกว่า 4 MiB |
| F03 | อัปโหลด PNG ที่ถูกต้อง | PNG ที่ถูกต้อง ขนาดน้อยกว่า 4 MiB |
| F04 | อัปโหลด OOXML ที่ถูกต้อง | DOCX หรือ PPTX ขั้นต่ำที่มีเส้นทางภายในตามที่ระบบกำหนด ขนาดน้อยกว่า 4 MiB |
| F05 | ทดสอบขนาดขอบเขต | ไฟล์ชนิดที่รองรับ ขนาดเท่ากับ 4,194,304 ไบต์ และลายเซ็นถูกต้อง |
| F06 | ทดสอบไฟล์เกินขนาด | ไฟล์ที่มีลักษณะถูกต้องแต่มีขนาด 4,194,305 ไบต์ |
| F07 | ทดสอบ MIME ไม่ตรงกับลายเซ็น | ใช้ข้อมูลไฟล์ที่ถูกต้องแต่แจ้ง MIME type เป็นอีกชนิดหนึ่งที่ระบบอนุญาต |
| F08 | ทดสอบข้อมูลไม่ถูกต้อง | Base64 ผิดรูปแบบ หรือถอดรหัสแล้วได้ข้อมูลว่าง |
| F09 | ทดสอบชนิดไฟล์ที่ไม่รองรับ | ไฟล์สังเคราะห์ประเภท executable/archive หรือ MIME ที่ไม่รองรับ โดยต้องไม่สร้างไฟล์ใน Drive |

F01–F05 เป็นกรณีที่คาดว่าจะผ่าน ส่วน F06–F09 เป็นกรณีที่คาดว่าจะถูกปฏิเสธ Manifest ฉบับสุดท้ายต้องบันทึกชื่อไฟล์ ค่า SHA-256 จำนวนไบต์ MIME type นามสกุล และผลที่คาดหวัง ห้ามใส่ Base64 หรือเนื้อหาไฟล์ใน Log หรือ GitHub

หากเจ้าของไม่อนุมัติการทดสอบขนาดขอบเขตหรือรูปแบบใด ให้ตัดกรณีนั้นออกและระบุเป็น NOT RUN ห้ามเปลี่ยนไปใช้ Fixture อื่นโดยไม่ได้รับอนุมัติ

## 7. ผู้ทดสอบและตารางสิทธิ์

ใช้เฉพาะผู้ใช้จำลองที่มีอยู่ใน Core Fixture เจ้าของโครงการต้องระบุการจับคู่ผู้ใช้จริงกับบทบาทเหล่านี้ใน Manifest ที่จำกัดสิทธิ์ เอกสารนี้จะไม่กำหนด User ID หรืออีเมลขึ้นเอง

| บทบาท | สิทธิ์ในระบบที่คาดหวัง | สิทธิ์ Drive หลังแนบไฟล์สำเร็จ |
|---|---|---|
| ผู้ส่ง/ผู้ส่งงานรายบุคคล | อัปโหลดไฟล์ของตนและเข้าถึง Submission ที่แนบแล้ว | Viewer |
| หัวหน้ากลุ่ม/ผู้ส่งงานกลุ่ม | แนบไฟล์ที่เข้าเงื่อนไขและส่งงานกลุ่มได้ | Viewer |
| สมาชิกกลุ่มที่ยังใช้งานและเป็นผู้ส่งไฟล์รอแนบ | อัปโหลดไฟล์สำหรับ Assignment เดียวกัน แต่ส่งงานไม่ได้หากไม่ใช่ตัวแทนกลุ่ม | Viewer หลังแนบไฟล์ |
| สมาชิกกลุ่มอื่นที่ยังใช้งาน | ดู Submission ของกลุ่มได้ | Viewer |
| สมาชิกเดิมที่พ้นสถานะ/ไม่ Active | ไม่ควรได้รับสิทธิ์จากการเป็นสมาชิกปัจจุบัน | ไม่เพิ่มสิทธิ์ Viewer ใหม่ |
| ผู้สอนที่ได้รับมอบหมายและยัง Active | ดู Submission ของ Offering ที่รับผิดชอบได้ | Viewer |
| ผู้สอนที่ไม่ได้รับมอบหมาย | ไม่มีสิทธิ์ เว้นแต่มีบทบาทอื่นที่อนุญาตอย่างชัดเจน | ไม่เพิ่มสิทธิ์ Viewer |
| ผู้ใช้ที่ไม่เกี่ยวข้อง | ไม่มีสิทธิ์ในระบบ | ไม่มี Viewer และเปิด URL โดยตรงไม่ได้ |
| บัญชีเจ้าของระบบ/เจ้าของ Drive | อาจมีสิทธิ์ระดับผู้ดูแลจากการเป็นเจ้าของ | ต้องบันทึกแยก ห้ามใช้สิทธิ์ของเจ้าของเป็นหลักฐานว่าผู้ใช้ทั่วไปมีสิทธิ์ถูกต้อง |

ผู้ใช้ที่ได้รับสิทธิ์สืบทอดจากโฟลเดอร์แม่หรือนโยบายโดเมน ไม่เหมาะเป็นผู้ทดสอบกรณีปฏิเสธสิทธิ์ หากแยกเงื่อนไขนี้ไม่ได้ ให้ระบุกรณี ACL ที่เกี่ยวข้องเป็น BLOCKED

| S2-FR-05 | จำลองการเขียน Submission ขั้นหลังล้มเหลวหลังแชร์ไฟล์สำเร็จ | Rollback พยายามคืนข้อมูลไฟล์ สถานะล็อกกลุ่ม และสิทธิ์ ต้องตรวจทุกทรัพยากรแยกกัน |

| S2-FR-07 | ตรวจว่าการกู้คืนไม่เรียก LINE หรือบริการภายนอก | ตัวนับ Stub ยืนยันว่าไม่มีการเรียกภายนอกจริง และคืนค่าฟังก์ชันแจ้งเตือนเดิมแล้ว |

ห้ามจำลองข้อผิดพลาดด้วยการเพิกถอนสิทธิ์ของผู้ใช้จริง เปลี่ยนสิทธิ์โฟลเดอร์ที่ไม่เกี่ยวข้อง หรือลบข้อมูลเดิม ห้ามจำลอง Rollback failure หากยังไม่ได้ทบทวนและอนุมัติจุดจำลองกับวิธีกู้คืนอย่างชัดเจน

## 9. ขั้นตอนดำเนินงานและมาตรการความปลอดภัย

### ระยะ A — เตรียมการแบบอ่านอย่างเดียว

1. ดึง Branch `development`, `CURRENT.md` และไฟล์ Backend/Test ที่เกี่ยวข้องฉบับล่าสุด
2. ยืนยันบันทึกปิด WP-SUB-1 และรักษาข้อมูลทดสอบเดิมทั้งหมด
3. ตรวจตัวตนโฟลเดอร์ TEST รายการไฟล์ และสิทธิ์การแชร์แบบอ่านอย่างเดียว โดยไม่สร้างหรือเปลี่ยนแปลงสิ่งใด
4. ยืนยันการจับคู่ผู้ใช้จำลอง ความพร้อมของ Assignment/Group และอีเมลจากข้อมูลอ่านอย่างเดียว
5. บันทึกข้อมูลพื้นฐานแบบระบุ ID ที่แน่นอน และค่า Hash ของ Source
6. จัดทำรายงาน Preflight โดยไม่มีการเขียนข้อมูล ไม่มีการสร้างไฟล์ Drive ไม่มีการเปลี่ยนสิทธิ์ และไม่มีการเรียกบริการภายนอก

หากพบข้อมูลไม่ตรงกันหรือมีส่วนที่ยังไม่ทราบ ให้หยุด

### ระยะ B — พัฒนา Runner (ต้องอนุมัติแยกต่างหาก)

เมื่อเจ้าของอนุมัติแผน โฟลเดอร์ ผู้ทดสอบ ชุดไฟล์ จุดจำลองข้อผิดพลาด และการจัดการไฟล์หลังทดสอบแล้วเท่านั้น

1. เพิ่ม Runner สำหรับ WP-SUB-2 และเครื่องมือตรวจสอบหลังทดสอบแบบอ่านอย่างเดียวใน Branch `development`
2. ใช้ Handler ของแอปพลิเคชันสำหรับการทำงานทางธุรกิจ ห้ามข้าม Handler ไปเขียน Sheet โดยตรง
3. ติดตั้ง Stub แจ้งเตือนในหน่วยความจำและตรวจสอบก่อนเรียกคำสั่งใดที่อาจเรียกการแจ้งเตือน ต้องคืนค่าฟังก์ชันเดิมใน `finally` และเส้นทางจัดการข้อผิดพลาด
4. ห้ามติดตั้ง Trigger หรือเรียก LINE/`UrlFetchApp`
5. บันทึก Drive File ID และ Row ID ที่สร้างขึ้นลง Manifest ที่จำกัดสิทธิ์ทันทีหลังได้รับผลสำเร็จ Log ทั่วไปให้แสดงเฉพาะจำนวน/ค่า Boolean
6. ใช้ Request ID ที่ไม่ซ้ำและเป้าหมายที่ไม่ซ้ำ ห้ามทำกรณีที่เสร็จแล้วซ้ำ
7. จัดให้มี Entry Point สำหรับ GAS Editor ที่ไม่ต้องส่ง Argument และแยกฟังก์ชัน Preflight ออกจาก Persistent Runner
8. หยุดเมื่อมีการเขียนข้อมูลที่ไม่คาดหมาย Rollback ล้มเหลว ไฟล์ไม่ตรง Manifest สิทธิ์ผิด Manifest บันทึกไม่ได้ หรือการทำงานถูกขัดจังหวะ

### ระยะ C — เจ้าของโครงการรัน Preflight

เจ้าของคัดลอกเฉพาะไฟล์ Preflight ที่ได้รับอนุมัติไปยัง GAS TEST และรัน Preflight แบบอ่านอย่างเดียว จากนั้นส่ง Execution Log ฉบับเต็มที่ปกปิดข้อมูลอ่อนไหวแล้ว

การมีไฟล์ Runner ไม่ได้แปลว่าได้รับอนุญาตให้รัน Persistent Runner จะรันได้ต่อเมื่อเจ้าของตรวจผล READY และอนุมัติการรันถาวรตามขอบเขตที่ระบุแยกต่างหากเท่านั้น

### ระยะ D — การรันทดสอบแบบมีการเปลี่ยนแปลงข้อมูลหนึ่งครั้ง

1. รัน Persistent Runner ที่อนุมัติแล้วเพียงครั้งเดียว
2. หากการทำงานหยุดชะงัก สถานะไม่สิ้นสุด หรือเกิดข้อผิดพลาด ห้ามรันซ้ำ
3. เรียกเฉพาะเครื่องมือสรุป Manifest และตรวจสอบแบบอ่านอย่างเดียวที่อนุมัติแล้ว
4. ตรวจสอบ Drive ID, Metadata ID, Submission ID, Audit ID และสิทธิ์จริงให้ครบก่อนตัดสินใจขั้นต่อไป
5. หาก Rollback ไม่สมบูรณ์ ให้หยุดและรอคำสั่งจากเจ้าของ

### ระยะ E — ปิดงาน

ปิด WP-SUB-2 ได้เมื่อ:
- ทุกกรณีที่กำหนดมีผลรันจริงจากเจ้าของครบถ้วน
- การตรวจสอบ ID และรายการไฟล์ Drive ผ่าน
- สิทธิ์ที่มีผลจริงตรงกับตารางบทบาท
- ไม่มีไฟล์ตกค้าง ข้อมูลตกค้าง Submission Audit หรือสิทธิ์ที่ไม่สามารถอธิบายได้
- คืนค่า Notification Stub แล้ว และไม่มีการเรียกบริการภายนอกจริง
- ข้อมูลพื้นฐานเดิมยังคงอยู่
- เจ้าของยอมรับข้อจำกัดของหลักฐานและตัดสินใจเรื่องการจัดเก็บไฟล์ทดสอบแล้ว

ห้ามใช้เพียงข้อความสถานะสุดท้ายทั่วไปของ Runner เป็นหลักฐานปิดงาน ต้องมีรายละเอียดผลแต่ละกรณีและการตรวจสอบแยกต่างหาก

## 10. ข้อกำหนด Manifest และ Log

Manifest ที่จำกัดสิทธิ์ควรบันทึกข้อมูลต่อไปนี้

- รุ่นของแผนและค่า Hash ของขอบเขตที่อนุมัติ
- เครื่องหมาย TEST และ Blob SHA ของ Source
- จำนวนและ ID ข้อมูลพื้นฐานก่อนทดสอบ
- ข้อมูลอ้างอิงโฟลเดอร์ Drive ที่อนุมัติ (เก็บในส่วนจำกัดสิทธิ์ ห้ามพิมพ์ใน Log ทั่วไป)
- การจับคู่บทบาทผู้ใช้จำลอง
- ชื่อไฟล์ Fixture ค่า SHA-256 MIME type และจำนวนไบต์
- สถานะของแต่ละกรณีและ Request ID
- Drive File ID, SubmissionFile ID, Submission ID, Audit ID และการเปลี่ยนสิทธิ์ที่เกิดขึ้น
- ความพยายามและผล Rollback
- จำนวนการเรียก Stub และสถานะการคืนค่าฟังก์ชัน
- ผลตรวจสอบหลังทดสอบและสถานะสุดท้าย

Log ทั่วไปต้องไม่เปิดเผย ID ดิบ อีเมลส่วนบุคคล Base64 เนื้อหาไฟล์ Access Token Folder ID Drive URL หรือข้อมูลส่วนบุคคล ให้แสดงเฉพาะจำนวน ค่า Boolean บทบาท และ Error Code ที่ปกปิดแล้ว

ต้องออกแบบการบันทึก Manifest ไม่ให้กรณีทดสอบที่ล้มเหลวค้างอยู่ในสถานะ `IN_PROGRESS` โดยไม่มีเครื่องหมายหยุดและตรวจสอบ หากบันทึก Manifest อย่างปลอดภัยไม่ได้ ให้หยุด ห้ามรันซ้ำ

## 11. การเก็บไฟล์และขอบเขต Cleanup

แผนนี้ไม่อนุญาตให้ทำ Cleanup

ก่อนพัฒนา เจ้าของต้องเลือกและอนุมัติการจัดการไฟล์ทดสอบทุกไฟล์ ได้แก่
- เก็บไว้ในโฟลเดอร์ TEST เพื่อให้เจ้าของตรวจด้วยตนเอง หรือ
- จัดทำแผน Cleanup แยก โดยระบุ ID ของไฟล์อย่างแน่นอน และขออนุมัติหลังการตรวจสอบเสร็จสมบูรณ์

ห้ามลบอัตโนมัติ ย้ายไฟล์ทดสอบที่สำเร็จไปถังขยะ ล้างโฟลเดอร์ทั้งหมด หรือใช้เป้าหมาย Cleanup เดิมของ WP-SUB-1 ซ้ำ การ Rollback ภายใน Handler เมื่อเกิดข้อผิดพลาดเป็นคนละเรื่องกับการอนุญาต Cleanup หลังทดสอบ หาก Rollback ทิ้งไฟล์ค้าง ให้รักษาไฟล์และหลักฐานไว้จนกว่าเจ้าของจะอนุมัติการจัดการเฉพาะรายการ

## 12. ความเสี่ยงและประเด็นที่ต้องพิจารณา

1. **ความเสี่ยงด้านสิทธิ์ Drive ที่มีผลจริง:** การตั้งโฟลเดอร์เป็น Private เป็นเงื่อนไขจำเป็นแต่ไม่เพียงพอ ต้องตรวจสิทธิ์ระดับไฟล์โดยตรง
2. **การตรวจอีเมลผู้ส่ง:** Source ปัจจุบันไม่ได้ปฏิเสธอย่างชัดเจนเมื่อไม่พบข้อมูล User/Email ก่อนดำเนินการต่อ ต้องยืนยันพฤติกรรมจริงและพิจารณาว่าต้องแก้ Source หรือไม่ ห้ามแก้ไขภายใต้การอนุมัติแผนทดสอบนี้โดยปริยาย
3. **ความเสี่ยง Rollback สิทธิ์:** ข้อผิดพลาดในการเพิกถอนสิทธิ์อาจถูกดักจับและบันทึกเป็นข้อความทั่วไป หาก Rollback ไม่แน่นอนต้อง STOP ไม่ใช่ PASS
4. **การเขียนข้อมูลหลายระบบไม่เป็นธุรกรรมเดียว:** Drive, Sheets และ ACL ไม่ได้เปลี่ยนแปลงแบบ Atomic พร้อมกัน ต้องตรวจทรัพยากรแต่ละส่วน
5. **การสืบทอดสิทธิ์ของโฟลเดอร์:** โฟลเดอร์อาจแสดงว่าเป็น Private แต่ยังมีสิทธิ์จากโฟลเดอร์แม่หรือ Shared Drive ต้องตรวจแบบมีผลจริง
6. **บัญชีเจ้าของและบัญชีผู้รัน:** ตัวตนของบัญชี GAS และเจ้าของไฟล์มีผลต่อสิทธิ์ ต้องบันทึกให้ชัดเจน
7. **กิจกรรมพร้อมกัน:** ผู้ใช้หรือ Trigger อื่นใน TEST อาจเปลี่ยนแถวหรือสิทธิ์ระหว่างทดสอบ ต้องกำหนดช่วงเวลาที่แยกจากการใช้งานอื่น
8. **ผลข้างเคียงจากการแจ้งเตือน:** การสร้าง Submission อาจเรียกการแจ้งเตือน ต้องติดตั้ง Stub ก่อนการทำงานแรกและตรวจสอบการคืนค่า

- [ ] ตัดสินใจการจัดการไฟล์หลังทดสอบ โดย Cleanup ต้องอนุมัติแยก
- [ ] อนุมัติการพัฒนา Preflight/Runner และเครื่องมือตรวจสอบหลังทดสอบแบบอ่านอย่างเดียว

การอนุมัติแผนนี้ไม่ถือเป็นการอนุญาตให้รัน Persistent Runner อัปโหลดไฟล์ เปลี่ยนสิทธิ์ ลบไฟล์ Deploy หรือทำรายการอื่นที่อยู่นอกขอบเขต การดำเนินการเหล่านั้นต้องได้รับอนุมัติแยกต่างหากและระบุขอบเขตให้ชัดเจน

## 14. สถานะปัจจุบัน

**สถานะ WP-SUB-2: อนุมัติแผนการทดสอบแล้ว — การพัฒนาและการดำเนินการยังต้องได้รับอนุมัติแยกต่างหาก**

ไม่มีการพัฒนาโค้ด WP-SUB-2 ไม่มี Runner หรือ Preflight ไม่มีการรัน GAS ไม่มีการอัปโหลดหรือสร้างไฟล์ใน Drive ไม่มีการเปลี่ยนสิทธิ์ ไม่มี Migration, Trigger, Deployment, LINE, External Network Call หรือ Cleanup ภายใต้เอกสารฉบับนี้
