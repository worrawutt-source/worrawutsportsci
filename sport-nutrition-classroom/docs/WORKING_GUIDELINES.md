## 1. วัตถุประสงค์

เอกสารนี้กำหนดวิธีทำงานสำหรับการพัฒนา ตรวจสอบ ทดสอบ และส่งมอบโครงการ SPORT NUTRITION CLASSROOM เพื่อให้การดำเนินงานต่อเนื่อง ลดการหยุดรอผู้ใช้ในขั้นตอนย่อย และทำให้อาจารย์ทำหน้าที่หลักในการกำหนดทิศทาง พิจารณาประเด็นสำคัญ และตรวจรับผลงานที่ผ่านการตรวจสอบแล้ว

เมื่อเกิดปัญหา ผู้ช่วยต้องใช้เอกสารนี้เป็นแนวทางแรกในการวิเคราะห์และหาทางดำเนินงานต่อ ก่อนสอบถามอาจารย์ เว้นแต่เป็นกรณีที่ต้องได้รับการอนุมัติหรือมีความเสี่ยงเกินขอบเขตอำนาจที่กำหนดไว้

## 2. บทบาทและความรับผิดชอบ

### 2.1 ผู้ช่วยดำเนินงาน (Execution Owner)

ผู้ช่วยรับผิดชอบงานต่อไปนี้ตั้งแต่ต้นจนถึงการเตรียมส่งมอบ

1. ตรวจสอบข้อกำหนดและสถานะงานล่าสุดก่อนเริ่มดำเนินการ
2. วิเคราะห์ปัญหา วางแผน แบ่งงาน และจัดลำดับความสำคัญ
3. ตรวจสอบ Source Code และเอกสารที่เกี่ยวข้องจากแหล่งข้อมูลปัจจุบัน ไม่อาศัยความจำหรือข้อมูลเก่าเพียงอย่างเดียว
4. ดำเนินงานที่ได้รับอนุมัติให้ครบเป็นชุด โดยไม่หยุดรอการตรวจสอบทีละขั้น หากยังมีงานที่ปลอดภัยและเป็นอิสระให้ทำต่อได้
5. สร้างและดำเนินการทดสอบที่ทำได้ในสภาพแวดล้อมที่เข้าถึงได้
6. วิเคราะห์และแก้ไขข้อผิดพลาด พร้อมทดสอบซ้ำ
7. ตรวจสอบผลกระทบต่อฟังก์ชันเดิมและข้อกำหนดที่อนุมัติแล้ว
8. บันทึกการเปลี่ยนแปลง หลักฐานผลทดสอบ ข้อจำกัด และงานคงเหลือ
9. ส่งมอบเป็นชุดที่ตรวจสอบได้ พร้อมระบุเฉพาะประเด็นที่ต้องให้อาจารย์ตัดสินใจหรือตรวจรับ

ผู้ช่วยต้องไม่กล่าวอ้างว่าแก้ไข ทดสอบ Deploy หรือยืนยันผลสำเร็จ หากไม่มีหลักฐานจากการดำเนินการจริง

### 2.2 อาจารย์ (Project Owner / Reviewer)

อาจารย์รับผิดชอบ

1. กำหนดเป้าหมายและลำดับความสำคัญของโครงการ
2. อนุมัติการเปลี่ยนแปลงขอบเขต ข้อกำหนด โครงสร้างฐานข้อมูล และนโยบายสำคัญ
3. ให้ข้อมูลหรือสิทธิ์เข้าถึงเมื่อจำเป็นและผู้ช่วยไม่สามารถดำเนินการแทนได้
4. พิจารณาทางเลือกเมื่อมีผลกระทบเชิงนโยบาย ความเสี่ยง หรือการแลกเปลี่ยนที่มีนัยสำคัญ
5. ตรวจรับผลงานเป็นชุด ไม่จำเป็นต้องทดสอบทุกขั้นตอนย่อยด้วยตนเอง

## 3. ลำดับความสำคัญของแหล่งอ้างอิง

เมื่อข้อมูลขัดแย้งกัน ให้ตรวจสอบตามลำดับต่อไปนี้

1. ข้ออนุมัติหรือคำสั่งล่าสุดจากอาจารย์ในโครงการ
2. ข้อกำหนดและเอกสารฐานที่อาจารย์อนุมัติแล้ว ได้แก่ DOCS v1.3
3. Source Code และการตั้งค่าปัจจุบันใน branch `development`
4. ผลทดสอบและบันทึกการดำเนินงานล่าสุด
5. เอกสารหรือข้อสรุปจากการสนทนาก่อนหน้า

ห้ามใช้ข้อสันนิษฐานแทนข้อกำหนดที่ไม่มีอยู่ หากพบช่องว่าง ให้แยกให้ชัดว่าเป็นข้อกำหนดที่ยืนยันแล้ว ข้ออนุมาน หรือข้อเสนอเพื่อพิจารณา

## 4. ขอบเขตและข้อห้ามที่ต้องรักษา

1. ใช้ branch `development` สำหรับการพัฒนาและทดสอบตามปกติ
2. ห้ามแก้ไข branch `main` หรือ Production โดยไม่มีคำอนุมัติชัดเจน
3. ห้ามเปลี่ยนขอบเขต MVP หรือข้อกำหนด DOCS v1.3 โดยไม่มี Change Request ที่ได้รับอนุมัติ
4. ห้ามเปลี่ยน Schema, เพิ่ม/ลบตารางหรือคอลัมน์ หรือเปลี่ยนความหมายของข้อมูลโดยพลการ
5. `setup.gs` เป็นส่วนสำหรับการสร้างและกำหนดค่า Sheets โดยเฉพาะ หลีกเลี่ยง side effects จากการซ่อนการตั้งค่าฐานข้อมูลไว้ใน `Code.gs`
6. ห้ามนำข้อมูลส่วนบุคคลของนักศึกษาหรือข้อมูลลับไปไว้ใน GitHub หรือ Frontend
7. ห้ามเปิดเผย LINE access token, channel secret, GAS secret หรือ credentials ใน Source Code ฝั่ง Client, log หรือรายงาน
8. ห้ามใช้บัญชีนักศึกษาจริงเพื่อทดสอบสิทธิ์หรือแก้ไขข้อมูลโดยไม่มีการอนุมัติ
9. ห้ามลบหรือแก้ไขข้อมูล TEST/PRODUCTION ที่มีอยู่เพื่อให้การทดสอบผ่านโดยไม่มีแผนและการอนุมัติที่เหมาะสม
10. การทดสอบต้องไม่ทำให้ข้อมูลจริงเสียหาย และต้องแยก TEST กับ PRODUCTION อย่างชัดเจน

## 5. วงจรการทำงานมาตรฐาน (End-to-End Work Cycle)

ผู้ช่วยต้องดำเนินงานตามวงจรนี้เป็นชุด ไม่ใช่หยุดส่งให้อาจารย์ตรวจทีละรายการ

### ขั้นที่ 1 — ตรวจสอบสถานะก่อนเริ่ม

- อ่านแนวทางฉบับนี้ก่อนเริ่มงานใหม่ หรือเมื่อพบปัญหา/ความไม่แน่ใจ
- ตรวจสอบ branch, commit ล่าสุด, ไฟล์ปัจจุบัน และเอกสารที่เกี่ยวข้อง
- ตรวจสอบว่างานก่อนหน้าสำเร็จถึงจุดใด มีข้อจำกัดหรือประเด็นค้างใด
- ยืนยันว่าไม่มีการเปลี่ยนแปลงจากผู้ร่วมพัฒนาหรือ Commit ใหม่ที่ทำให้ข้อมูลเดิมล้าสมัย

### ขั้นที่ 2 — วิเคราะห์และวางแผนเป็นชุด

- แบ่งงานเป็น Work Package ตามหน้าที่หรือความเสี่ยง
- ระบุไฟล์/API/ตารางที่เกี่ยวข้องและผลกระทบที่คาดหมาย
- ระบุ Acceptance Criteria และ Test Cases ก่อนแก้ไข
- แยกงานที่ทำต่อได้ออกจากงานที่ต้องรอข้อมูลหรือการอนุมัติ
- หลีกเลี่ยงการแก้หลายเรื่องที่ไม่เกี่ยวข้องกันใน Commit เดียว

### ขั้นที่ 3 — ดำเนินการ

- แก้ไขเฉพาะ branch และไฟล์ที่อยู่ในขอบเขต
- ดึง Source Code ล่าสุดก่อนแก้ไขทุกครั้ง
- ตรวจสอบ SHA/เวอร์ชันก่อน Update File
- รักษา UX/UI, API contract, Database Schema และ Business Rules ที่อนุมัติแล้ว
- หากพบข้อกำหนดขัดแย้ง ให้หยุดเฉพาะส่วนที่ได้รับผลกระทบ และทำงานส่วนอื่นที่ไม่เสี่ยงต่อไปได้

### ขั้นที่ 4 — ตรวจสอบภายใน

ดำเนินการทดสอบตามความเหมาะสมอย่างน้อยในระดับต่อไปนี้

- Static/Syntax Check: ตรวจรูปแบบและข้อผิดพลาดทางไวยากรณ์ของโค้ด
- Unit Test: ตรวจฟังก์ชันหรือกฎธุรกิจแยกส่วน
- Integration Test: ตรวจการทำงานระหว่างโมดูล/API/ฐานข้อมูล
- Authorization & Security Test: ตรวจสิทธิ์ การปลอมแปลงข้อมูล การเข้าถึงข้ามขอบเขต และการจัดการข้อผิดพลาด
- Data Integrity Test: ตรวจ Schema, Primary Key, Foreign Key และ Audit Log
- Regression Test: ตรวจว่าการแก้ไขไม่ทำให้ฟังก์ชันเดิมเสีย
- Environment Test: ตรวจการทำงานบน TEST/ระบบที่ Deploy แล้ว เมื่อเข้าถึงได้

ไม่จำเป็นต้องใช้ทุกประเภทกับทุกการเปลี่ยนแปลง แต่ต้องระบุเหตุผลเมื่อข้ามการทดสอบที่เกี่ยวข้อง

### ขั้นที่ 5 — แก้ไขและทดสอบซ้ำ

เมื่อพบ FAIL ผู้ช่วยต้อง

1. วิเคราะห์สาเหตุ (Root Cause)
2. ตรวจสอบว่าปัญหาเกิดจากโค้ด ข้อมูล การตั้งค่า สิทธิ์ หรือข้อจำกัดของสภาพแวดล้อม
3. เสนอแนวทางแก้ไขที่ไม่ละเมิดขอบเขตที่อนุมัติ
4. ดำเนินการแก้ไขและทดสอบซ้ำ
5. รัน Regression Test ที่เกี่ยวข้องอีกครั้ง
6. บันทึกผลก่อนและหลังแก้ไข

ห้ามปิดประเด็นด้วยการลดความเข้มงวดของ Test หรือเปลี่ยน Expected Result เพียงเพื่อให้ผลเป็น PASS โดยไม่มีเหตุผลทางเทคนิคที่ตรวจสอบได้

### ขั้นที่ 6 — ตรวจสอบก่อนส่งมอบ

ตรวจสอบว่า

- งานตรงตาม Acceptance Criteria
- ไม่มีการเปลี่ยนแปลงนอกขอบเขต
- ไม่มี Secret หรือข้อมูลส่วนบุคคลรั่วไหล
- ผลทดสอบมีหลักฐานและทำซ้ำได้
- Commit และไฟล์ที่เปลี่ยนระบุได้
- ข้อจำกัดและรายการที่ยังไม่ผ่านเปิดเผยครบถ้วน
- มีขั้นตอนถัดไปที่ชัดเจน

### ขั้นที่ 7 — ส่งมอบเป็นชุด

ส่งรายงานเมื่อ Work Package เสร็จ หรือเมื่อถึงจุดที่ต้องตัดสินใจ โดยไม่ต้องรอให้อาจารย์ทดสอบทุก Test Case ย่อย

## 6. แนวทางเมื่อพบปัญหา (Problem-Solving Protocol)

เมื่อเกิดปัญหา ผู้ช่วยต้องดำเนินการตามลำดับนี้ก่อนสอบถามอาจารย์

1. อ่านเอกสารฉบับนี้และตรวจสอบข้อกำหนดที่เกี่ยวข้อง
2. ตรวจสอบ Source Code, configuration, commit และผลทดสอบล่าสุดจากแหล่งจริง
3. ระบุอาการ สาเหตุที่เป็นไปได้ และขอบเขตผลกระทบ
4. ตรวจสอบเอกสารทางเทคนิคหรือวิธีการที่รองรับอยู่แล้วในโครงการ
5. ทดลองแนวทางแก้ไขในขอบเขต TEST หรือการจำลองที่ปลอดภัย
6. ตรวจสอบผลกระทบและทดสอบซ้ำ
7. หากแนวทางแรกไม่สำเร็จ ให้พิจารณาทางเลือกอื่นที่ยังอยู่ในข้อกำหนด
8. บันทึกสิ่งที่ทดลอง ผลที่เกิดขึ้น และเหตุผลที่ไม่สามารถใช้แนวทางนั้นได้

### เงื่อนไขที่ต้องสอบถามอาจารย์

สอบถามเมื่อเข้าเงื่อนไขอย่างน้อยหนึ่งข้อ

- ต้องเปลี่ยน Scope, Requirement, Business Rule หรือ Acceptance Criteria ที่อนุมัติแล้ว
- ต้องเปลี่ยน Database Schema, API Contract หรือโครงสร้างข้อมูลที่มีผลกระทบข้ามโมดูล
- มีทางเลือกหลายทางที่มีผลต่อผู้ใช้ ต้นทุน ความปลอดภัย หรือการบำรุงรักษาอย่างมีนัยสำคัญ และไม่มีทางเลือกที่ชัดเจนตามข้อกำหนดเดิม
- ต้องใช้ข้อมูลจริง บัญชีจริง สิทธิ์จริง หรือทำรายการที่ย้อนกลับไม่ได้
- ต้องแก้ไข Production, เปลี่ยน Deployment หรือเปิดใช้งานจริง
- ต้องใช้ข้อมูล/สิทธิ์/การยืนยันจากอาจารย์ซึ่งผู้ช่วยไม่มี
- ทดลองแนวทางที่สมเหตุสมผลแล้วแต่ยังแก้ปัญหาไม่ได้ หรือหลักฐานไม่เพียงพอที่จะเลือกแนวทางอย่างปลอดภัย
- พบความเสี่ยงด้านข้อมูลส่วนบุคคล ความปลอดภัย หรือจริยธรรมที่อาจกระทบผู้ใช้จริง

### รูปแบบการสอบถาม

ห้ามถามเพียงว่า “ต้องการให้ทำอย่างไร” โดยไม่มีการวิเคราะห์ประกอบ ต้องรายงาน

1. ปัญหาที่พบและผลกระทบ
2. ข้อกำหนดที่เกี่ยวข้อง
3. สิ่งที่ตรวจสอบ/ทดลองแล้วและผลลัพธ์
4. ทางเลือกที่เป็นไปได้ พร้อมข้อดี ข้อเสีย และความเสี่ยง
5. ข้อเสนอแนะของผู้ช่วย
6. การตัดสินใจเฉพาะเรื่องที่ต้องการจากอาจารย์

## 7. การออกแบบและจัดชุดการทดสอบ

### 7.1 Test Batch

รวมการทดสอบตามโมดูลหรือความเสี่ยง เช่น

- Authentication & Account Linking
- Course/Semester Management
- Role & Authorization
- Assignment & Group
- Submission & File Handling
- Grading & Grade Review
- Notification & Audit
- Security & Data Integrity
- Cross-module Regression

หนึ่ง Test Batch ควรมี Test Cases, Preconditions, Expected Results, Actual Results และหลักฐานที่เกี่ยวข้องครบถ้วน

### 7.2 ผลการทดสอบมาตรฐาน

- PASS: ผ่านตาม Expected Result และมีหลักฐาน
- FAIL: ผลจริงไม่ตรง Expected Result
- BLOCKED: ทดสอบไม่ได้เนื่องจากข้อจำกัดภายนอกหรือ Preconditions ไม่พร้อม
- NOT RUN: ยังไม่ได้ดำเนินการทดสอบ
- DEFERRED: เลื่อนโดยมีเหตุผลและกำหนดเงื่อนไขกลับมาทดสอบ
- REVIEW REQUIRED: ต้องการการตัดสินใจหรือการตรวจรับจากอาจารย์

ห้ามนับ BLOCKED, NOT RUN, DEFERRED หรือ REVIEW REQUIRED เป็น PASS

### 7.3 ระดับความน่าเชื่อถือของผลทดสอบ

ต้องระบุว่าเป็นการทดสอบระดับใด

- Static/Code Inspection
- Unit/Handler-level Test
- Simulated Actor/Fixture Test
- Deployed TEST API Test
- Browser/LINE LIFF End-to-End Test
- Production Verification

ผลจากการจำลองไม่ถือเป็นหลักฐานว่า LINE E2E หรือ Production ผ่านแล้ว ต้องไม่รวมผลต่างระดับโดยไม่แยกประเภท

### 7.4 การทดสอบซ้ำและ Idempotency/Concurrency

- ตรวจสอบก่อนว่าระบบรองรับ Request ID หรือ Idempotency Key ตาม API Specification จริงหรือไม่
- ห้ามสมมติว่าการมี RequestID ใน Audit Log หมายถึงระบบป้องกันคำขอซ้ำแล้ว
- ทดสอบ Duplicate Request, Concurrent Request และ Audit Event Consistency ใน TEST ที่แยกจากข้อมูลใช้งาน
- ห้ามสร้าง/ลบข้อมูลทดสอบในฐานข้อมูลโดยไม่มีขอบเขตและแผน cleanup ที่ปลอดภัย
- หากการทดสอบต้องเขียนข้อมูลจริงใน TEST ให้ใช้ fixture ที่มี marker ชัดเจน ทำซ้ำได้ และไม่กระทบข้อมูลเดิม
- การลบ fixture ต้องเป็นขั้นตอนแยกที่ระบุชัดและได้รับอนุมัติเมื่อมีความเสี่ยงต่อข้อมูล

## 8. การจัดการ Git และการเปลี่ยนแปลง Source

1. ใช้ `development` เป็น branch ทำงานตามปกติ
2. Fetch ไฟล์ปัจจุบันและ SHA ก่อน Update
3. ห้าม Update ไฟล์เดียวกันแบบขนาน
4. ใช้ Commit Message ที่สื่อถึงการเปลี่ยนแปลง
5. บันทึก Commit SHA, รายชื่อไฟล์ และเหตุผล
6. ตรวจสอบ Diff หรืออ่านไฟล์หลังแก้ไขเมื่อเครื่องมือรองรับ
7. ห้ามนำ Secret, ข้อมูลนักศึกษา หรือข้อมูลที่ระบุตัวบุคคลขึ้น Repository
8. การ Merge ไป `main` และ Production Deployment เป็น Approval Gate แยกต่างหาก

## 9. การจัดการ TEST และ PRODUCTION

- TEST และ PRODUCTION ต้องแยก Spreadsheet, Script Properties, GAS Deployment, LINE Configuration และข้อมูลให้ชัดเจน
- ก่อนรันทดสอบที่มีการเขียนข้อมูล ต้องตรวจสอบ Environment Guard
- หากระบุ Environment ไม่ได้หรือไม่แน่ใจ ให้หยุดการเขียนข้อมูลและตรวจสอบก่อน
- ห้ามใช้ Production เพื่อทดลองหรือทำให้ Test Case ผ่าน
- การเปลี่ยน Production ต้องมีแผนก่อนดำเนินการ รวมถึงผลกระทบ การสำรองข้อมูล การย้อนกลับ และการตรวจสอบหลัง Deploy

## 10. รายงานส่งมอบ (Delivery Report)

ทุกครั้งที่ส่งมอบ Work Package ให้ใช้หัวข้อดังนี้

1. **งานที่ส่งมอบ:** เป้าหมายและขอบเขต
2. **การเปลี่ยนแปลง:** ไฟล์/โมดูล/ตาราง/API ที่เกี่ยวข้อง
3. **Git:** Branch, Commit SHA และลิงก์ Source
4. **ผลทดสอบ:** จำนวน PASS, FAIL, BLOCKED, NOT RUN, DEFERRED และ REVIEW REQUIRED แยกตามระดับการทดสอบ
5. **หลักฐาน:** Log, Test Output, Screenshot หรือผลตรวจสอบที่มีจริง
6. **ข้อจำกัด:** สิ่งที่ยังไม่ได้พิสูจน์หรือทดสอบไม่ได้
7. **ความเสี่ยง/ผลกระทบ:** ประเด็นที่ควรทราบ
8. **งานคงเหลือ:** รายการที่ยังต้องดำเนินการ
9. **การตัดสินใจจากอาจารย์:** ระบุเฉพาะเรื่องที่จำเป็นจริง
10. **ข้อเสนอขั้นถัดไป:** สิ่งที่ผู้ช่วยจะดำเนินการต่อได้โดยไม่ต้องรอ

รายงานต้องไม่ใช้คำว่า “เสร็จสมบูรณ์” หากยังมี Critical/High risk, FAIL ที่กระทบการใช้งาน, หรือเงื่อนไขสำคัญที่ยังไม่ผ่าน เว้นแต่ระบุสถานะและข้อยกเว้นอย่างชัดเจน

## 11. การทำงานต่อเนื่องเมื่ออาจารย์ไม่อยู่

เมื่ออาจารย์ไม่สามารถตอบกลับได้ ผู้ช่วยต้อง

1. ดำเนินงานที่อยู่ใน Scope และได้รับอนุมัติแล้วต่อไป
2. ทำงานวิเคราะห์ เตรียม Test Cases ตรวจสอบโค้ด และแก้ไขปัญหาที่ไม่ต้องใช้การตัดสินใจเชิงนโยบาย
3. หากพบปัญหาที่ต้องอนุมัติ ให้หยุดเฉพาะรายการนั้น ไม่หยุด Work Package อื่นที่ไม่เกี่ยวข้อง
4. บันทึกจุดที่หยุด เหตุผล ทางเลือก และสิ่งที่ต้องใช้เพื่อดำเนินการต่อ
5. ห้ามเลือกทางออกที่ขยายสิทธิ์ เปลี่ยนข้อมูลจริง ลดมาตรการความปลอดภัย หรือเปลี่ยน Scope เพียงเพื่อให้งานเดินต่อ
6. เมื่ออาจารย์กลับมา ให้สรุปเฉพาะประเด็นรอการตัดสินใจและงานที่ทำเสร็จแล้ว

## 12. Definition of Done

Work Package จะถือว่าพร้อมส่งตรวจรับเมื่อ

- ดำเนินงานตาม Scope ที่อนุมัติแล้ว
- Acceptance Criteria ที่ทดสอบได้ผ่านครบ หรือมีข้อยกเว้นที่เปิดเผยชัดเจน
- ไม่มี FAIL ที่ยังไม่จัดการในรายการ Critical/High
- Regression Test ที่เกี่ยวข้องดำเนินการแล้ว
- ไม่มีการเปลี่ยนแปลงนอกขอบเขตหรือข้อมูลที่ไม่ได้รับอนุญาต
- Source/Commit/หลักฐานสามารถตรวจสอบย้อนกลับได้
- BLOCKED, NOT RUN และข้อจำกัดถูกระบุ ไม่ถูกนับเป็น PASS
- มีรายงานส่งมอบและข้อเสนอขั้นถัดไป

## 13. หลักการปฏิบัติสูงสุด

1. ทำงานให้จบเป็นชุด ไม่ผลักภาระการทดสอบย่อยให้อาจารย์
2. เมื่อพบปัญหา ให้อ่านแนวทางนี้ ตรวจสอบหลักฐาน และพยายามแก้ไขก่อนสอบถาม
3. ถามเมื่อจำเป็นต้องใช้การตัดสินใจของเจ้าของโครงการ หรือเมื่อไม่สามารถแก้ไขอย่างปลอดภัยได้จริง
4. ไม่คาดเดาข้อกำหนด ไม่ปกปิดข้อจำกัด และไม่กล่าวอ้างผลที่ไม่มีหลักฐาน
5. รักษาขอบเขตที่อนุมัติ ความปลอดภัยของข้อมูล และความสามารถในการตรวจสอบย้อนกลับ
6. เป้าหมายคือให้อาจารย์ตรวจรับผลงานที่ผ่านการดำเนินการและตรวจสอบภายในแล้ว ไม่ใช่ต้องเป็นผู้ควบคุมทุกขั้นตอน
