## 1. วัตถุประสงค์และขอบเขตการอนุมัติ

เอกสารนี้แปลงแผนการทดสอบ WP-SUB-2 ให้เป็นข้อกำหนดการออกแบบเครื่องมือ Google Apps Script (GAS) สองส่วนที่แยกจากกันอย่างชัดเจน

1. **Preflight** — ตรวจสอบความพร้อมของ Source Code การตั้งค่า โฟลเดอร์ TEST ความพร้อมของผู้ทดสอบ และข้อมูลพื้นฐาน โดยอ่านข้อมูลเท่านั้น ห้ามสร้าง แก้ไข แชร์ ย้ายไปถังขยะ หรือลบไฟล์ใน Drive ห้ามเขียน Sheet หรือ Script Properties ห้ามติดตั้งหรือเรียก Trigger ห้ามส่งการแจ้งเตือน และห้ามเรียกบริการภายนอก
2. **Runner** — ดำเนินการทดสอบแบบมีการบันทึกสถานะถาวร โดยใช้ Handler ของระบบและดำเนินการกับ Google Drive เฉพาะรายการที่ได้รับอนุมัติอย่างชัดเจน เป็นเครื่องมือแยกจาก Preflight และห้ามถูกเรียกโดยเป็นผลข้างเคียงของ Preflight

เอกสารนี้เป็นข้อเสนอการออกแบบเท่านั้น ไม่ได้อนุญาตให้พัฒนาโค้ด คัดลอกโค้ดไปยัง GAS รัน Preflight รัน Runner อัปโหลดไฟล์ เพิ่ม/เพิกถอนสิทธิ์ เปลี่ยน Script Properties หรือทำ Cleanup

### 2.1 พฤติกรรมของ Source Code ที่เกี่ยวข้อง

- การอัปโหลดใน `FileManagement.gs` รองรับ MIME type และลายเซ็นไฟล์ตามที่ระบุในไฟล์ดังกล่าว โดยกำหนด `FM_MAX_BYTES_ = 4 * 1024 * 1024` และตรวจแพ็กเกจ OOXML ด้วยการแตกไฟล์และตรวจเส้นทางภายในที่กำหนด รวมถึงจำกัดขนาดหลังแตกไฟล์ไว้ที่ 20 MiB
- การอัปโหลดอ่าน Script Property `SNC_SUBMISSION_FOLDER_ID` แล้วเรียก `DriveApp.getFolderById` ตรวจว่า `folder.getSharingAccess() === DriveApp.Access.PRIVATE` สร้างไฟล์ใน Drive และพยายามเพิ่มสิทธิ์ Viewer ให้ผู้ส่ง
- เครื่องหมายสถานะรอแนบคือ `STAGED:<userId>:<assignmentId>`
- หากเพิ่มข้อมูลไฟล์หรือ AuditLog ไม่สำเร็จ ระบบพยายามชดเชยการเปลี่ยนแปลงที่เกิดขึ้น แต่ยังอาจมีไฟล์ Drive หรือข้อมูลตกค้างหากการชดเชยล้มเหลว จึงต้องตรวจแยกทุกทรัพยากร
- `file.access` ปฏิเสธไฟล์ที่ไม่มีข้อมูลหรือยังอยู่ในสถานะรอแนบ และตรวจสิทธิ์ Submission ในระดับแอปพลิเคชันก่อนคืน URL
- การแนบไฟล์กับ Submission ตรวจว่าไฟล์รอแนบเป็นของผู้ส่งหรือสมาชิกกลุ่มที่ยัง Active ใน Assignment เดียวกัน และพยายามเพิ่มสิทธิ์ Viewer ให้ผู้ส่ง สมาชิกกลุ่ม Active และผู้สอนที่ได้รับมอบหมาย
- Rollback ของ Submission เป็นการชดเชยการเปลี่ยนแปลงหลายส่วน ไม่ใช่ธุรกรรมเดียว โดยพยายามคืนข้อมูลไฟล์ แถว Submission สถานะล็อกกลุ่ม และสิทธิ์ Viewer ที่เพิ่มขึ้น
- การสร้าง Submission อาจเรียก `notifySubmissionReceived_` ซึ่งอาจส่งการแจ้งเตือนผ่าน LINE ด้วย `UrlFetchApp.fetch` ดังนั้น Runner ต้องป้องกันการแจ้งเตือนจริงและการเชื่อมต่อเครือข่ายก่อนเรียก Handler ใด ๆ

### 2.2 ประเด็นจากการตรวจ Source ที่ต้องรักษาไว้

1. การตรวจสถานะโฟลเดอร์ `PRIVATE` ไม่เท่ากับการพิสูจน์สิทธิ์ที่มีผลจริงของไฟล์ ต้องตรวจสิทธิ์โดยตรงและสิทธิ์ที่สืบทอดมาแยกกัน
2. ขั้นตอนอัปโหลดพยายามเพิ่มสิทธิ์ Viewer ให้ผู้ส่งเมื่อพบข้อมูล User และ Email เท่านั้น แต่ไม่ได้ปฏิเสธอย่างชัดเจนเมื่อไม่พบข้อมูลดังกล่าวในจุดนั้น Preflight ต้องตรวจข้อมูลผู้ทดสอบก่อนเริ่มการทดสอบแบบมีการเขียนข้อมูล
3. เส้นทาง Rollback ปัจจุบันอาจดักจับข้อผิดพลาดรองและบันทึกข้อความทั่วไป Runner ต้องไม่ถือว่าข้อความ Error จาก Handler เป็นหลักฐานว่า Rollback สำเร็จ
4. หากบันทึกสถานะ Runner ไม่ได้ ต้องถือเป็นเหตุให้หยุด ห้ามเริ่ม Runner ใหม่โดยอัตโนมัติ

## 5. ข้อกำหนด Preflight — ตรวจสอบแบบอ่านอย่างเดียว

### 5.1 เงื่อนไขที่ห้ามละเมิด

Preflight ต้อง:

- อ่านข้อมูลเท่านั้น
- ไม่เรียก `DriveApp.createFile`, `setTrashed`, `addViewer`, `removeViewer` หรือคำสั่งเปลี่ยนสิทธิ์ใด ๆ
- ไม่เขียน Sheets, Script Properties, PropertiesService, CacheService หรือ Manifest
- ไม่เรียก Business Handler ที่อาจเปลี่ยนข้อมูล
- ไม่ติดตั้ง ลบ หรือเรียก Trigger
- ไม่เรียก `UrlFetchApp`, LINE, อีเมล หรือบริการเครือข่ายภายนอก
- ไม่สร้างไฟล์หรือโฟลเดอร์ชั่วคราว
- ไม่เปิดเผย Folder ID, File ID, User ID, อีเมล, Drive URL, Token หรือเนื้อหาไฟล์ใน Log ทั่วไป

Preflight อ่านโฟลเดอร์ Drive ที่อนุมัติ โฟลเดอร์ย่อย Sheet ที่เกี่ยวข้อง ค่า Script Property และข้อมูลสิทธิ์ Drive ได้ หาก API ที่ใช้ตรวจสิทธิ์ไม่สามารถให้ข้อมูลเพียงพอที่จะยืนยันสิทธิ์ที่มีผลจริง ให้รายงาน BLOCKED/UNVERIFIED ห้ามอนุมานว่าผ่าน

| PF-07 | สถานะการแชร์โฟลเดอร์ | Sharing Access และรายละเอียดสิทธิ์ที่ตรวจได้ | PRIVATE/Restricted และไม่พบสิทธิ์กว้างที่ไม่อนุญาต | ไม่เป็น Private มีสิทธิ์กว้างสืบทอดมา หรือหลักฐานไม่เพียงพอ |
| PF-08 | รูปแบบสิทธิ์ที่มีผลจริง | ข้อมูลสิทธิ์โดยตรง/สืบทอดและบริบทบัญชี | พิสูจน์รูปแบบการจำกัดสิทธิ์ตามที่อนุมัติได้ | พบผู้ได้รับสิทธิ์ที่ไม่ทราบที่มา หรือตรวจไม่ได้ |
| PF-09 | บัญชีผู้รัน | ตัวตนบัญชี GAS ในรูปแบบที่ไม่เปิดเผยข้อมูลเกินจำเป็น และความสามารถเข้าถึง Drive | ตรงกับบัญชีที่เจ้าของอนุมัติ | ไม่ทราบหรือไม่มีสิทธิ์ |
| PF-10 | รายการ Fixture | ชื่อ ขนาด MIME และ Fixture Manifest | ตรงกันทั้งหมด ไม่มีไฟล์เกิน/ขาด | มีไฟล์ผิด เพิ่ม ขาด หรือไม่ได้อนุมัติ |
| PF-11 | การจับคู่ผู้ทดสอบ | ข้อมูล User จำลองและบทบาท | มีครบและแยกบทบาทได้ตามต้องการ | ขาด ซ้ำ หรือเป็นบัญชีบุคคลจริง |
| PF-12 | ความพร้อมของอีเมลผู้ทดสอบ | อีเมลจำลองที่ถูกต้องและแตกต่างกัน | ครบและเจ้าของอนุมัติ | ไม่มี ผิดรูปแบบ หรือใช้ซ้ำในกรณีที่ต้องแยก |
| PF-13 | ความพร้อมของ Assignment | สถานะ Assignment และความสัมพันธ์ Offering | เป้าหมายที่อนุมัติมีอยู่และเข้าเงื่อนไข | ปิดแล้ว ไม่พบ Offering ผิด หรือเคยใช้แล้ว |
| PF-14 | โครงสร้างกลุ่ม | สมาชิก Active ตัวแทนกลุ่ม สมาชิกเดิม และสถานะ | ตรงกับตารางบทบาทและข้อกำหนดกลุ่ม | สมาชิกหรือบทบาทกำกวม |
| PF-15 | Schema ของ Sheet | หัวตารางที่จำเป็นใน SubmissionFiles, Submissions, Groups, AuditLogs และตารางสนับสนุน | มีครบและไม่มีหัวตารางซ้ำ | ขาดหรือซ้ำ |
| PF-16 | ข้อมูลพื้นฐาน | ID แถวข้อมูลและรายการไฟล์ Drive ก่อนทดสอบ | บันทึกได้แบบอ่านอย่างเดียว ไม่มีรายการที่อธิบายไม่ได้ | ID ซ้ำ ไฟล์ไม่ทราบที่มา หรือข้อมูลพื้นฐานกำกวม |
| PF-17 | ความพร้อมของการแยกการแจ้งเตือน | ตรวจแบบจำลองว่า Stub ติดตั้ง/คืนค่าได้โดยไม่เรียกเครือข่ายจริง | ตรวจสอบการติดตั้งและคืนค่าได้จาก Source | ไม่สามารถรับประกันว่าไม่มีการเรียกภายนอก |
| PF-18 | กิจกรรมพร้อมกัน | เจ้าของยืนยันช่วงเวลาทดสอบแยกจากงานอื่น และข้อมูลอ่านอย่างเดียวคงที่ | ไม่มีการรันหรือใช้งานอื่นที่ชนกัน | พบการทำงานพร้อมกันหรือไม่ทราบสถานะ |
| PF-19 | ความพร้อมของ Manifest | รุ่นและขอบเขตที่อนุมัติ รวมถึงตำแหน่งเก็บ Manifest | ตำแหน่งจัดเก็บและสิทธิ์ได้รับอนุมัติ | ไม่ระบุหรือไม่มีการจำกัดสิทธิ์ |
| PF-20 | การจัดการไฟล์หลังทดสอบ | มีมติจากเจ้าของโครงการ | บันทึกแนวทางเก็บไฟล์แล้ว โดย Cleanup ยังแยกอนุมัติ | ยังไม่มีมติ |

### 5.3 รูปแบบผลลัพธ์ Preflight

Preflight ส่งคืนผลแบบปกปิดข้อมูลและบันทึกสรุปย่อ ประกอบด้วย

- `success`: เป็น true เมื่อการตรวจสอบทำงานจนจบเท่านั้น
- `status`: `READY`, `BLOCKED` หรือ `ERROR`
- `checksTotal`, `pass`, `fail`, `blocked`, `notRun`
- `sourceManifestMatch`
- `folderConfigMatch`
- `folderPrivate`
- `effectiveAclVerified`
- `actorMappingComplete`
- `assignmentTargetsEligible`
- `fixtureInventoryMatch`
- `baselineCapturedReadOnly`
- `externalCallsExpected=0`
- `writesExpected=0`
- `blockers`: รหัสรายการและเหตุผลที่ปกปิดข้อมูลแล้วเท่านั้น

จะรายงาน READY ได้เมื่อรายการบังคับทุกข้อผ่าน หากตรวจไม่ได้ ไม่ทราบ หรือหลักฐานไม่ชัดเจน ต้องเป็น BLOCKED ไม่ใช่ PASS ทั้งนี้ READY หมายถึงสถานะที่ตรวจพบในเวลานั้นตรงตามเงื่อนไขเท่านั้น ไม่ใช่การอนุญาตให้เริ่ม Runner

## 6. ข้อกำหนด Runner — การทดสอบแบบมีการเปลี่ยนแปลงข้อมูลอย่างควบคุม

### 6.1 เงื่อนไขบังคับก่อน Runner เปลี่ยนแปลงข้อมูล

ก่อนเริ่มการเปลี่ยนแปลงใด ๆ Runner ต้องตรวจครบทุกข้อดังนี้

1. ยืนยันว่าเป็นสภาพแวดล้อม TEST
2. Hash ของ Source ปัจจุบันตรงกับชุด Source ที่ตรวจสอบและอนุมัติแล้ว
3. ตัวตนโฟลเดอร์ Drive และการตั้งค่าตรงกับที่อนุมัติ
4. ผล Preflight เป็น READY และผูกกับรุ่นขอบเขต Source Manifest และ Fixture Inventory ชุดเดียวกัน
5. เจ้าของอนุมัติการรันแบบมีการเปลี่ยนแปลงข้อมูลแยกต่างหาก โดยระบุผู้ทดสอบ Assignment/Group Fixture จุดจำลองข้อผิดพลาด การดำเนินการ Drive และการจัดการไฟล์หลังทดสอบ
6. ไม่มี Runner WP-SUB-2 ก่อนหน้าที่ค้างหรือยังไม่ได้ตรวจสอบ
7. ไม่ใช้ ID หรือไฟล์ใด ๆ ของ WP-SUB-1 ซ้ำ
8. ติดตั้งและตรวจสอบระบบ Stub การแจ้งเตือนก่อนเรียก Handler ที่อาจแจ้งเตือน
9. ตำแหน่ง Manifest และวิธีกู้คืนพร้อมใช้งาน โดยผ่านกลไกที่ได้รับอนุมัติอย่างชัดเจน

หากไม่ผ่านข้อใด Runner ต้องออกก่อนสร้างไฟล์ Drive เปลี่ยนสิทธิ์ หรือเขียนข้อมูลธุรกิจ

### 6.2 สถานะการทำงาน (State Machine)

สถานะที่เสนอ:

- `NOT_STARTED`
- `PREFLIGHT_VERIFIED`
- `RUNNING`
- `STOPPED_REQUIRES_RECONCILIATION`
- `RECONCILED_WITH_REVIEW_ITEMS`
- `COMPLETE`
- `ABORTED_BEFORE_MUTATION`

กติกา:

- ใช้ `COMPLETE` ได้เมื่อทุกกรณีที่จำเป็นและการตรวจสอบแยกต่างหากผ่านทั้งหมด
- หากมีการเขียนข้อมูลที่ไม่คาดหมาย บันทึก Manifest ไม่ได้ Rollback ล้มเหลว สิทธิ์ผิด พบไฟล์ที่ไม่มีใน Manifest คืนค่า Stub ไม่สำเร็จ พบการเรียกภายนอก หรือการทำงานหยุดชะงัก ต้องเปลี่ยนเป็น `STOPPED_REQUIRES_RECONCILIATION`
- Run ที่หยุดหรือขาดช่วงห้ามเริ่มใหม่ตั้งแต่ต้นโดยเด็ดขาด
- ข้อกำหนดฉบับ 1.0.0 ยังไม่รวมฟังก์ชัน Resume หากต้องการทำต่อภายหลังต้องออกแบบและทบทวนแยก โดยใช้ผล Reconciliation ที่ระบุ ID แน่นอน
- Runner ต้องบันทึกเจตนาของกรณีทดสอบลง Manifest ก่อนเปลี่ยนข้อมูล บันทึก ID ที่ได้ทันทีหลังการเปลี่ยนแปลงสำเร็จ และบันทึกว่ากรณีนั้นเสร็จแล้วหลังตรวจเงื่อนไขผลลัพธ์ครบ
- หากบันทึก ID หลังเปลี่ยนข้อมูลไม่ได้ ให้หยุดและใช้การตรวจรายการ Drive/Sheet แบบอ่านอย่างเดียว ห้ามเดา ID หรือเรียกซ้ำ

### 6.3 การออกแบบ Manifest

Manifest ต้องอยู่ในตำแหน่ง TEST ที่เจ้าของอนุมัติและจำกัดสิทธิ์ เอกสารนี้ยังไม่เลือกกลไกจัดเก็บ ต้องได้รับอนุมัติก่อนพัฒนา ห้ามเลือก Sheet หรือ Script Property ที่อาจใช้ร่วมกับ Production หรือชุดทดสอบอื่นโดยพลการ

ข้อมูลใน Manifest ประกอบด้วย

- รุ่น Schema รุ่นแผน ค่า Hash ของขอบเขต Run Token และเวลาสร้าง
- เครื่องหมาย TEST และ Blob SHA ของ Source
- ผล Preflight และเวลาตรวจ
- ข้อมูลอ้างอิงโฟลเดอร์ที่อนุมัติ (เก็บในส่วนจำกัดสิทธิ์)
- การจับคู่บทบาทผู้ทดสอบ (ข้อมูลจำกัดสิทธิ์)
- เป้าหมาย Assignment และ Group ที่อนุมัติ (ข้อมูลจำกัดสิทธิ์)
- ชื่อ Fixture ค่า SHA-256 จำนวนไบต์ MIME type และนามสกุล
- ID ข้อมูลพื้นฐานก่อนทดสอบใน Sheet และรายการไฟล์ของโฟลเดอร์ Drive ทั้งสี่
- รหัสกรณี สถานะเจตนา Request ID บทบาทผู้กระทำ เป้าหมาย และการดำเนินการที่คาดหวัง
- Drive File ID, SubmissionFile ID, Submission ID, Audit ID และการเปลี่ยนสิทธิ์ที่เกิดขึ้น
- การพยายาม Rollback ผล และทรัพยากรที่ยังไม่คลี่คลาย
- ตัวนับ Notification Stub และสถานะการคืนค่าฟังก์ชัน
- ผล Reconciliation และสถานะสุดท้าย

Log ทั่วไปแสดงได้เฉพาะจำนวน ค่า Boolean รหัสกรณี Error Code ที่ปกปิด และสถานะ ห้ามแสดง ID ดิบ อีเมล เนื้อหาไฟล์ Base64 Drive URL หรือค่า Script Property

### 6.4 การแยกการแจ้งเตือน

- ก่อนเรียกคำสั่งแรกที่อาจแจ้งเตือน Runner ต้องแทนที่ฟังก์ชันแจ้งเตือนที่เกี่ยวข้องในหน่วยความจำด้วย Stub ที่กำหนดผลได้แน่นอน
- Stub บันทึกจำนวนครั้งและประเภทเหตุการณ์ที่ปกปิดแล้วเท่านั้น ห้ามเขียน NotificationLogs และห้ามเรียก LINE
- Runner ต้องมีการป้องกันกรณีเรียก `UrlFetchApp.fetch` โดยไม่ตั้งใจ Wrapper สำหรับทดสอบอาจโยน Error ที่กำหนดไว้และเพิ่มตัวนับในหน่วยความจำ แต่ต้องไม่ส่งคำขอเครือข่ายจริง
- บันทึก Function Reference เดิมก่อนแทนที่
- คืนค่าฟังก์ชันเดิมใน `finally` และตรวจสอบความเท่ากันของ Reference หลังคืนค่า
- หากคืนค่าไม่ได้หรือยืนยันไม่ได้ ให้หยุดและรายงาน BLOCKED/STOPPED ห้ามดำเนินกรณีถัดไป
- การตรวจ Source ต้องระบุเส้นทางการแจ้งเตือนทั้งหมดที่ Handler ที่เลือกสามารถเรียกได้ การแทนที่เพียง Hook เดียวไม่เพียงพอหากยังมีเส้นทางอื่นเรียก `ntSend_` ได้โดยตรง

### 6.5 ลำดับกรณีทดสอบที่เสนอ

ชุดกรณีสุดท้ายต้องเลือกจากแผนการทดสอบหลักและตารางผู้ใช้/Fixture/เป้าหมายที่เจ้าของอนุมัติแล้วเท่านั้น ลำดับที่เสนอมีดังนี้

**ชุด A — ตรวจสอบการอัปโหลด**
- กรณีผ่าน: PDF, JPEG, PNG, OOXML ที่อนุมัติ และไฟล์ขนาด 4 MiB พอดีหากได้รับอนุมัติ
- กรณีไม่ผ่าน: เกินขนาด MIME/ลายเซ็นไม่ตรง Base64 ผิดหรือว่าง และ MIME ที่ไม่รองรับ
- ทุกกรณีไม่ผ่านต้องตรวจว่าไม่มีไฟล์ Drive, แถว SubmissionFiles หรือ Audit upload ใหม่
- ทุกกรณีผ่านต้องบันทึก ID ไฟล์ Drive และข้อมูลไฟล์ทันที

**ชุด B — วงจรไฟล์รอแนบ**
- ตรวจว่าไฟล์ที่ยังรอแนบไม่สามารถเข้าถึงผ่าน `file.access`
- แนบไฟล์รายบุคคลและกลุ่มที่ได้รับอนุมัติผ่าน Handler
- ตรวจกรณีผู้ส่งไม่ถูกต้อง Assignment ไม่ตรง และสมาชิกกลุ่มไม่ Active ว่าถูกปฏิเสธโดยไม่เปลี่ยน Submission
- ใช้ Submission เป้าหมายที่ไม่ซ้ำและอนุมัติไว้ ห้ามใช้เป้าหมายเดิมซ้ำหรือแก้ไข Revision เว้นแต่ได้รับอนุมัติ

**ชุด C — ตรวจสิทธิ์ ACL**
- ตรวจสถานะสิทธิ์ Drive ก่อนและหลังแนบไฟล์
- ยืนยันว่าผู้ส่ง สมาชิกกลุ่ม Active และผู้สอนที่ได้รับมอบหมายได้รับ Viewer ตามที่กำหนด
- ยืนยันว่าอดีตสมาชิก ผู้สอนที่ไม่ได้รับมอบหมาย และผู้ใช้ที่ไม่เกี่ยวข้องไม่ได้รับสิทธิ์ใหม่
- แยกสิทธิ์โดยตรงและสิทธิ์สืบทอด หากสิทธิ์สืบทอดทำให้ทดสอบการปฏิเสธไม่ได้ ให้กรณีนั้นเป็น BLOCKED

**ชุด D — ข้อผิดพลาดและ Rollback**
- ทำเฉพาะจุดจำลองที่ได้รับอนุมัติแยกต่างหาก
- แต่ละจุดต้องระบุขอบเขตฟังก์ชันที่จำลอง สถานะบางส่วนที่คาดหวัง การชดเชย และหลักฐานแบบอ่านอย่างเดียวที่ต้องตรวจ
- ทำกรณีจำลองข้อผิดพลาดหลังกรณีผ่านทั้งหมด และใช้โฟลเดอร์/เป้าหมายที่กำหนดไว้
- หาก Rollback ไม่สมบูรณ์หรือไม่แน่นอน ให้หยุด Runner ทั้งชุด

**ชุด E — ตรวจสอบสถานะสุดท้าย**
- ทำหลัง Runner หยุดการเขียนข้อมูลและคืนค่า Notification Stub แล้วเท่านั้น
- เปรียบเทียบ ID พื้นฐานและ ID ใหม่ของ Sheet ที่เกี่ยวข้อง
- เปรียบเทียบรายการไฟล์ใหม่ในโฟลเดอร์ย่อยทั้งสี่กับ Manifest
- ตรวจความสัมพันธ์ไฟล์–Metadata–Submission–Audit
- ตรวจสิทธิ์โดยตรงและสิทธิ์สืบทอด
- ยืนยันว่าไม่มีสิทธิ์สาธารณะ/โดเมนที่ไม่คาดหมาย ไม่มีไฟล์ตกค้างที่อธิบายไม่ได้ และไม่มีข้อมูลเดิมสูญหาย
- รายงานผลแยกเป็นรายกรณี ห้ามใช้สถานะรวมปกปิดกรณีที่ไม่มีหลักฐาน

### 6.6 การป้องกันการทำงานซ้ำ

- ทุกกรณีต้องมี Case Key และ Request ID ที่ไม่ซ้ำและเปลี่ยนย้อนหลังไม่ได้
- Manifest ต้องบันทึก `INTENT_RECORDED` ก่อนเรียก Handler ที่เปลี่ยนข้อมูล
- กรณีที่มี Intent แต่ไม่มีผลลัพธ์สุดท้ายที่ยืนยันได้ ให้ถือว่ายังไม่คลี่คลาย ห้ามเรียกซ้ำ
- บันทึก ID ไฟล์หรือแถวข้อมูลที่ได้รับทันที หากบันทึกไม่ได้ให้หยุด
- ก่อนพิจารณาทำต่อในอนาคต ต้องตรวจสถานะจริงแบบอ่านอย่างเดียวและได้รับอนุมัติแผนทำต่อใหม่
- ห้ามพึ่งพา IdempotencyKeys ของแอปพลิเคชันเพียงอย่างเดียว เพราะการสร้างไฟล์ Drive เกิดก่อนขั้นตอนข้อมูลและ Audit บางส่วน จึงอาจเหลือไฟล์ตกค้างเมื่อขั้นตอนหลังล้มเหลว

## 7. เครื่องมือตรวจสอบหลังทดสอบแบบอ่านอย่างเดียว

เครื่องมือนี้ต้องแยกจาก Runner และห้ามเปลี่ยนแปลงข้อมูลใด ๆ

รายการตรวจสอบที่จำเป็น:

1. เปรียบเทียบ Primary ID เดิมกับข้อมูลปัจจุบันใน `SubmissionFiles`, `Submissions`, `Groups`, `GroupMembers` (เฉพาะเมื่อใช้เส้นทาง Group ที่อนุมัติ) และ `AuditLogs`
2. เปรียบเทียบ ID ที่ Manifest ระบุว่าสร้างใหม่กับแถวปัจจุบัน ระบุรายการที่หาย ซ้ำ หรือไม่ได้อยู่ใน Manifest
3. เปรียบเทียบ File ID ปัจจุบันในโฟลเดอร์ Drive ย่อยแต่ละโฟลเดอร์กับรายการก่อนทดสอบและ ID ที่ Manifest ระบุว่าสร้าง
4. ตรวจว่า Drive File แต่ละไฟล์เชื่อมกับ SubmissionFiles เพียงหนึ่งแถวตามที่กำหนด
5. ตรวจ Marker สถานะรอแนบสำหรับไฟล์ที่ควรยังรอแนบ และตรวจ SubmissionID สำหรับไฟล์ที่แนบแล้ว
6. ตรวจคู่ Action/Entity ใน Audit และ Entity ID ที่แน่นอน
7. ตรวจค่า Group Membership Lock ก่อน/หลัง เฉพาะกรณี Submission กลุ่มที่อนุมัติ
8. ตรวจสิทธิ์ที่มีผลจริงและเปรียบเทียบการเปลี่ยนสิทธิ์โดยตรง พร้อมรายงานสิทธิ์สืบทอดแยกต่างหาก
9. ตรวจการคืนค่า Notification Stub และหลักฐานว่าการเรียกบริการภายนอกจริงเป็นศูนย์
10. ส่งผล `PASS`, `FAIL`, `BLOCKED` หรือ `NOT_RUN` แยกตามรายการ พร้อมสถานะรวมที่ปกปิดข้อมูล

เครื่องมือตรวจสอบห้ามย้ายไฟล์ไปถังขยะ ลบไฟล์ เพิกถอนสิทธิ์ ซ่อมข้อมูล Metadata หรือเขียน Manifest ใหม่ ให้รายงานทรัพยากรที่ยังไม่คลี่คลายใน Manifest ที่จำกัดสิทธิ์ และแสดงเฉพาะข้อมูลอ้างอิงที่ปกปิดแล้วใน Log ทั่วไป

## 8. ลำดับการดำเนินงานและจุดอนุมัติ

| จุดอนุมัติ | กิจกรรม | อนุญาตให้เปลี่ยนข้อมูลหรือไม่ | การตัดสินใจจากเจ้าของ |
|---|---|---:|---|
| G0 | อนุมัติข้อกำหนดและขอบเขตฉบับนี้ | ไม่ได้ | อนุมัติ/ขอแก้ไขการออกแบบ |
| G1 | พัฒนาเฉพาะ Preflight บน `development` | ไม่เปลี่ยนข้อมูลขณะรัน | อนุมัติขอบเขตการพัฒนา |
| G2 | เจ้าของคัดลอก Preflight ไป TEST GAS และรัน | ไม่เปลี่ยนข้อมูล | อนุมัติการรันแบบอ่านอย่างเดียว |
| G3 | ตรวจรายงาน Preflight และแก้ประเด็นขัดข้อง | ไม่เปลี่ยนข้อมูล | ยืนยันผล READY |
| G4 | พัฒนา Runner และ Reconciliation บน `development` | เปลี่ยนได้เฉพาะไฟล์ใน Repository | อนุมัติการพัฒนาและขอบเขตการรันถาวร |
| G5 | เจ้าของคัดลอกเครื่องมือที่อนุมัติไป TEST GAS | ยังไม่เปลี่ยน Drive | ยืนยันการซิงก์ Source กับ GAS |
| G6 | เจ้าของอนุมัติ Persistent Run หนึ่งครั้งอย่างชัดเจน | ได้ เฉพาะขอบเขตที่อนุมัติ | อนุมัติ Run Token ช่วงเวลา ผู้ทดสอบ Fixture เป้าหมาย และการจัดการไฟล์ |
| G7 | เจ้าของรัน Runner | ได้ เฉพาะขอบเขตที่อนุมัติ | ส่ง Log ฉบับเต็มที่ปกปิดข้อมูลแล้ว |
| G8 | ตรวจสอบหลังทดสอบแบบอ่านอย่างเดียวและพิจารณาปิดงาน | ไม่ได้ | ยอมรับหลักฐานและแนวทางจัดการไฟล์ |

การอนุมัติแต่ละจุดไม่ครอบคลุมจุดถัดไป โดยเฉพาะการอนุมัติข้อกำหนดฉบับนี้ไม่ใช่การอนุญาตให้พัฒนา Runner หรือรัน Runner

## 9. เงื่อนไขที่ต้องหยุดทันที

หยุดการทำงานและเก็บหลักฐานทั้งหมด หากเกิดเหตุการณ์ใดเหตุการณ์หนึ่งต่อไปนี้

- สภาพแวดล้อมหรือ Source ไม่ตรงกับที่อนุมัติ
- Folder ID ชื่อ หรือโฟลเดอร์แม่ไม่ตรง
- โฟลเดอร์ไม่เป็น Private หรือพิสูจน์สิทธิ์ที่มีผลจริงไม่ได้
- พบไฟล์ที่ไม่คาดหมายในโฟลเดอร์ทดสอบ
- บทบาท/อีเมลผู้ทดสอบ Assignment หรือ Group ไม่ตรงกับที่อนุมัติ
- Manifest ไม่มี อ่านไม่ได้ หรือบันทึกสถานะไม่ได้
- มีไฟล์หรือแถวข้อมูลที่ไม่ได้บันทึกใน Manifest
- กรณีที่ควรถูกปฏิเสธกลับสร้างข้อมูลถาวร
- ผลการเพิ่ม/เพิกถอนสิทธิ์ไม่แน่นอน
- Rollback ล้มเหลวหรือพิสูจน์ความสำเร็จได้ไม่ครบ
- ติดตั้งหรือคืนค่า Notification Stub ไม่ได้
- ตรวจพบการเรียก LINE/UrlFetch/บริการภายนอกจริง หรือไม่สามารถยืนยันว่าไม่มีการเรียกได้
- พบกิจกรรม TEST อื่นที่ทำงานพร้อมกัน
- การทำงานถูกขัดจังหวะหรือจบโดยไม่มีสถานะสุดท้ายใน Manifest

หลังหยุด ให้เรียกเฉพาะเครื่องมือตรวจสอบแบบอ่านอย่างเดียว ห้ามรัน Runner ซ้ำ ลบไฟล์ เพิกถอนสิทธิ์ หรือซ่อมแถวข้อมูล หากยังไม่มีแผนระบุ ID ที่แน่นอนและการอนุมัติแยกต่างหาก

## 10. การตัดสินใจที่เจ้าของโครงการยังต้องให้ข้อมูล

ภาพหน้าจอยืนยันโครงสร้างโฟลเดอร์ที่ต้องการ แต่ยังไม่ยืนยันความปลอดภัยและความพร้อมในการใช้งานจริง ก่อนจุด G1/G4 ต้องพิจารณาและยืนยันรายการต่อไปนี้

1. ยืนยันว่า Folder ID และโฟลเดอร์แม่ในข้อ 3 ถูกต้อง
2. ยืนยันว่าโฟลเดอร์อยู่ใน My Drive หรือ Shared Drive และระบุบัญชี GAS ที่จะใช้รัน
3. แสดงหลักฐานเจ้าของโฟลเดอร์ General access แบบ Restricted สิทธิ์โดยตรง/สืบทอด และการเข้าถึงจากกลุ่มหรือโดเมน
4. ยืนยันว่า Script Property `SNC_SUBMISSION_FOLDER_ID` ชี้ไปยังโฟลเดอร์นี้ ห้ามส่งค่า ID ดิบในแชต Preflight จะเปรียบเทียบค่าในระบบเอง
5. ยืนยันว่าโฟลเดอร์ย่อยทั้งสี่ใช้เฉพาะ WP นี้ และระบุไฟล์เดิมที่ต้องเก็บไว้เป็นข้อมูลพื้นฐาน
6. อนุมัติชุด Fixture จำลองและวิธีนำไฟล์ไบนารีเข้าสู่ GAS
7. อนุมัติ Assignment รายบุคคล/กลุ่มที่มีอยู่ และการจับคู่บทบาทผู้ทดสอบ รวมถึงอีเมลจำลองที่แตกต่างกัน
8. ยืนยันตำแหน่งจัดเก็บ Manifest และข้อจำกัดสิทธิ์
9. อนุมัติจุดจำลองข้อผิดพลาดและหลักฐานการคืนค่าฟังก์ชัน
10. เลือกการจัดการไฟล์ที่อัปโหลดสำเร็จ: เก็บให้เจ้าของตรวจ หรือจัดทำแผน Cleanup แยกซึ่งต้องอนุมัติชัดเจน
11. กำหนดช่วงเวลาทดสอบที่ไม่มีงาน TEST อื่นชนกัน
12. พิจารณาว่าพฤติกรรมปัจจุบันกรณีไม่มีอีเมลผู้ส่งต้องแก้ Source แยกหรือไม่ ห้ามรวมการแก้ไขระบบนี้เข้าในงาน Runner โดยปริยาย

## 11. รายการนอกขอบเขต

- Production, Branch `main`, Deployment, API/LIFF/Browser E2E และ UAT
- WP-SUB-3 และโมดูลอื่นที่ไม่เกี่ยวข้อง
- Migration, Schema Change, การติดตั้ง/ลบ Trigger, Email, LINE, UrlFetch หรือเครือข่ายภายนอก
- ข้อมูลจริงของนักศึกษา/ผู้สอน หรือเอกสารส่วนบุคคล
- การทดสอบถดถอยวงกว้าง หรือการเรียก Runner ของ WP-SUB-1/Assignment & Group ซ้ำ
- Cleanup อัตโนมัติ การล้างโฟลเดอร์ การซ่อมสิทธิ์ หรือการลบไฟล์ตกค้าง
- การแก้ Source Code ของแอปพลิเคชันที่ยังไม่ได้รับอนุมัติแยกต่างหาก
